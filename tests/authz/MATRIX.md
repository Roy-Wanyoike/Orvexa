### D7 — #90 `internal/interactions (+internal/telephony, internal/messaging call paths)` (reproduced this run (HTTP 409))

Second+ interaction-plane create WITHOUT provider_ref returns 409 interaction.duplicate: the service binds an empty ProviderRef as '' instead of NULL, so UNIQUE (tenant_id, provider, provider_ref) collapses every ref-less create per (tenant, provider) — POST /api/v1/interactions, /calls and /messages all refuse a legitimate second create (calls/messages take no provider_ref at all)

Repro: POST /api/v1/interactions/ twice for one tenant with bodies lacking ProviderRef — the 2nd returns 409 interaction.duplicate although nothing was duplicated (no idempotency key, no provider ref, fresh UUID). Secure behavior: 201 — dedupe must key on a real idempotency key, never on the absence of one

### D8 — #98 `internal/interactions (ListByConversation) + internal/cases (ListNotes)` (reproduced this run (HTTP 200))

Sub-resource LIST routes do not verify the parent resource's tenancy: GET /api/v1/conversations/{foreign-id}/interactions and GET /api/v1/cases/{foreign-id}/notes return 200 with an empty list instead of the canonical 404 (GET of the parent itself correctly 404s). No data leaks and no enumeration oracle exists (foreign and missing ids behave identically), but the responses are inconsistent with the 404-canonical contract the rest of the API enforces

Repro: With tenant-B's key, GET /api/v1/conversations/<tenant-A conversation UUID>/interactions → 200 {data:[]} (expect 404); same for GET /api/v1/cases/<tenant-A case UUID>/notes. Secure behavior: 404 like every other foreign-id route

### D9 — #99 `internal/telephony (ApplyAction → provider error mapping)` (reproduced this run (HTTP 500))

POST /api/v1/calls/{id}/actions with action hold|resume on a voice interaction that never went through POST /api/v1/calls/ (e.g. a voice interaction created via the generic interactions plane, or an inbound call opened by a provider webhook) returns 500 internal.error: telephony.ApplyAction propagates the provider's unknown-leg error unwrapped instead of mapping it to a typed app error

Repro: Create a voice interaction via POST /api/v1/interactions/ (channel=voice, any customer), then POST /api/v1/calls/{that id}/actions with {"action":"hold"} → 500 {internal.error} (expect a typed 4xx, e.g. 409 call.unknown_leg / 422; 200 after a fix that makes hold a no-op on unplaced legs)

## Notes & scope

- **100% route accounting:** every registration in `MountV1` (v1.go) is probed above — customers, conversations, interactions, agents, queues, cases, calls, messages, routing (+presence), AI, workflows, analytics, search — plus the public webhook ingress, the authenticated index, platform health endpoints and the conditional identity surface.
- **Search degradation:** the route is mounted and authenticated in every deployment; in this devstack run OpenSearch is off, so the honest typed `503 search.not_configured` is the correct success signal. When OpenSearch is configured the tenant filter is derived server-side from the authenticated principal (no tenant parameter exists on the wire).
- **Webhook ingress** is public by design (providers cannot hold API keys): the evidence rows prove signature fail-closed behavior, including that API keys confer nothing there.
- **Capability RBAC** (migration 0012 / [O-29]) is exercised for API-key principals via the mounted capability middleware (scope `{api}` passes; tenant-B tool calls are policy-refused 403 on a foreign AI agent).
- **Defect policy (issue #40):** failures are NOT fixed in this package. Each DEFECT row has a filed `type/bug` issue (section above); the ratchet rows keep the suite green only while the platform behaves exactly as recorded, and auto-re-verify once a fix lands.
- No credential material is committed: keys are minted per run and masked in this report; the webhook HMAC secret is a fixed test fixture.
